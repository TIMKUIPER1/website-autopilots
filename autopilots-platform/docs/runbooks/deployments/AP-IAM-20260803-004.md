## Identity boundary

`autopilots:health-monitor` is a service principal, not a Supabase Auth user or
an IAM human profile. Database constraints permanently set `login_allowed` and
`external_writes_allowed` to false. It has three allowlisted portfolio scopes:

- `monitoring.health.write`
- `monitoring.lease.manage`
- `monitoring.freshness.read`

Each scope is bound to the Autopilots legal entity and may be narrowed to an
operating brand. Cross-entity brand references are rejected by composite
foreign keys. Browser roles have no table privileges or RPC execution rights.

Monitoring v2 stores either a historical human authority or a service
principal, never both. New runs require the service principal. Lease uniqueness
now includes legal entity, so multiple future organizations cannot block one
another when using the same scheduler key and bucket.

## Suspension and recovery

Set the principal status to `suspended` only through an authorized IAM change.
All new lease, heartbeat, completion, freshness and health-evidence calls then
fail closed. Set `MONITORING_SCHEDULER_ENABLED=false` before planned suspension
to avoid noisy failed runtime state. Existing health, incident, run and audit
evidence remains append-only. Never attach a provider credential or login to
this principal; future external workloads require separate identities and
authorization.
