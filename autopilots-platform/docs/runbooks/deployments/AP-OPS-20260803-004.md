## Boundary

`integration.monitoring_runs` stores one unique lease for each scheduler key
and deterministic time bucket. Only `service_role` can claim, heartbeat,
complete or read freshness through the allowlisted RPCs. Since
`AP-IAM-20260803-004`, the v2 contract also requires the dedicated
`autopilots:health-monitor` service principal. Human profiles can no longer
execute machine leases and the audit actor is the service principal.

A running lease can be recovered only after its bounded expiry. The new holder
increments `attempt_count`; a previous holder cannot heartbeat or complete the
run. Completion accepts only the fixed outcomes, four numeric count fields and
an allowlisted error code. Every completion writes R0 audit evidence with
`externalWrites=false`.

Freshness is calculated from the latest persisted health event per governed
product connector. It reports `fresh`, `stale` or `never_observed`; it does not
claim that current product health is known merely because the scheduler process
is running.

## Recovery

Set `MONITORING_SCHEDULER_ENABLED=false` and restart the runtime. Do not delete
monitoring runs, health events, incidents or audit evidence. A stuck running
lease may expire naturally and be recovered by the next authorized instance.
Investigate repeated recoveries before re-enabling scheduling. Existing manual
read-only probes remain available.
